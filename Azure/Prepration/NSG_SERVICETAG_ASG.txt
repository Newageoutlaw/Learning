Azure **Network Security Groups (NSGs)** are a key component in Azure's network security model. They allow you to control inbound and outbound traffic to network interfaces (NICs), Virtual Machines (VMs), and subnets within a Virtual Network (VNet). NSGs act as virtual firewalls that define rules to filter traffic based on source and destination IP addresses, ports, and protocols.

### Key Concepts of Azure NSG

1. **Network Security Rules**:
   - NSGs consist of **security rules** that define the conditions under which traffic is allowed or denied. Each rule contains the following components:
     - **Priority**: The priority is a number between 100 and 4096 that determines the order of rule evaluation. Lower numbers have higher priority.
     - **Direction**: Specifies whether the rule applies to **inbound** or **outbound** traffic.
     - **Protocol**: Defines the protocol (TCP, UDP, or Any).
     - **Source/Destination**: Specifies the source or destination IP address ranges (can be a specific IP or CIDR block).
     - **Port Range**: Defines the allowed or denied ports (e.g., 80 for HTTP, 443 for HTTPS).
     - **Action**: Specifies whether to **Allow** or **Deny** traffic that matches the rule.

2. **Scope of NSGs**:
   - **Network Interface Level (NIC)**: Apply NSGs directly to a VM's network interface. This is useful when you need to restrict traffic to specific VMs.
   - **Subnet Level**: Apply NSGs to entire subnets within a Virtual Network. This can help secure an entire subnet of VMs or resources in a VNet.
   - **Combination**: You can apply NSGs at both the subnet and NIC levels. In this case, both sets of rules are evaluated, and the most restrictive rule is applied (i.e., deny always takes precedence over allow).

3. **Default Rules**:
   - Azure automatically creates a set of **default rules** in every NSG that cannot be deleted, but can be overridden by user-defined rules. These default rules include:
     - **Allow inbound traffic from the virtual network**.
     - **Allow inbound traffic from Azure load balancers**.
     - **Deny all inbound traffic from the internet**.
     - **Allow all outbound traffic** (except for specific restrictions).
   - These default rules provide a basic security baseline, but you should typically define custom rules for more precise control over network traffic.

4. **Rule Evaluation**:
   - **First Match Wins**: When evaluating traffic, Azure processes the rules in order of their priority (from 100 to 4096). The first rule that matches the traffic is applied. If no rule matches, the default rules are used.
   - **Implicit Deny**: If no rule explicitly allows the traffic, it is denied by default, as a "deny all" rule is always implied at the end of the evaluation process.

### Example of How to Configure an NSG

Suppose you have a Virtual Machine (VM) in a subnet and want to configure NSG rules to control its access:

1. **Allow HTTP traffic to a VM**:
   - **Direction**: Inbound
   - **Priority**: 100 (high priority)
   - **Protocol**: TCP
   - **Source**: Any (0.0.0.0/0)
   - **Source Port Range**: *
   - **Destination**: Any
   - **Destination Port Range**: 80 (HTTP)
   - **Action**: Allow

2. **Deny all traffic from a specific IP address**:
   - **Direction**: Inbound
   - **Priority**: 200
   - **Protocol**: Any
   - **Source**: 192.168.1.10 (a specific IP address)
   - **Destination**: Any
   - **Destination Port Range**: *
   - **Action**: Deny

3. **Allow SSH from specific IP addresses**:
   - **Direction**: Inbound
   - **Priority**: 300
   - **Protocol**: TCP
   - **Source**: 203.0.113.0/24 (specific IP range)
   - **Destination**: Any
   - **Destination Port Range**: 22 (SSH)
   - **Action**: Allow

### How to Apply NSGs

- **To a Virtual Machine (NIC Level)**: 
  1. Create an NSG in the Azure Portal.
  2. Create rules within the NSG (allow or deny specific traffic).
  3. Associate the NSG with the network interface of the VM.

- **To a Subnet (Subnet Level)**:
  1. Create an NSG in the Azure Portal.
  2. Create rules in the NSG.
  3. Associate the NSG with a subnet in your Virtual Network.
  4. All VMs and resources in the subnet will be subject to the rules defined in that NSG.

### Common Use Cases for NSGs

1. **Securing Web Servers**:
   - For example, to only allow **HTTP (port 80)** and **HTTPS (port 443)** traffic to a web server, while blocking everything else. 
   - **Allow inbound TCP traffic on port 80 (HTTP) and port 443 (HTTPS)** from any source, while denying all other inbound traffic.

2. **Restricting Access to Specific IPs**:
   - If you want to restrict access to a VM or subnet to a specific IP address or range (e.g., an on-premises network or a specific office location), you can define source IP-based rules.

3. **Controlling Outbound Traffic**:
   - You can also control outbound traffic. For instance, restricting the VMs in a subnet to only communicate with a specific destination, such as another subnet or an external service.
   - Example: Deny all outbound internet traffic except for access to a specific database or service.

4. **Restricting Access to Management Interfaces**:
   - You can limit access to management interfaces like **RDP (Remote Desktop)** or **SSH** to only trusted IP addresses.
   - Example: Only allow SSH (port 22) to a VM from a trusted office network's IP range.

### Advanced Features of NSGs

1. **Service Tags**: 
   - Instead of specifying IP ranges for certain Azure services, you can use **service tags** to represent a group of IP addresses for specific services.
   - For example, you can use the `AzureLoadBalancer` tag to allow traffic from the Azure Load Balancer to your VM without needing to define the IP ranges.

2. **Application Security Groups (ASGs)**:
   - **ASGs** allow you to group VMs and apply NSG rules based on the group name instead of individual NICs or IPs. This makes it easier to manage security for dynamic workloads.

3. **Flow Logs**:
   - Azure NSG **Flow Logs** provide visibility into the network traffic flowing through your NSG rules. This can be useful for troubleshooting, auditing, and monitoring network activity.

4. **Network Watcher**: 
   - With **Azure Network Watcher**, you can monitor and diagnose network traffic in your environment, helping you track traffic patterns and ensure that your NSG rules are functioning as expected.

### Example NSG Rule Order:
Let's say you have the following rules:

| Rule # | Direction | Priority | Source IP       | Destination IP   | Protocol | Port   | Action |
|--------|-----------|----------|-----------------|------------------|----------|--------|--------|
| 1      | Inbound   | 100      | Any             | Any              | TCP      | 80     | Allow  |
| 2      | Inbound   | 200      | Any             | Any              | TCP      | 443    | Allow  |
| 3      | Inbound   | 300      | 10.1.1.1        | Any              | TCP      | 22     | Deny   |
| 4      | Inbound   | 400      | Any             | Any              | TCP      | 22     | Allow  |

In this case:
- Rule 1 allows HTTP traffic on port 80 from any source.
- Rule 2 allows HTTPS traffic on port 443.
- Rule 3 denies SSH traffic from a specific IP (`10.1.1.1`).
- Rule 4 allows SSH traffic on port 22 from any source (but rule 3 takes precedence for `10.1.1.1`).

If an incoming SSH request is from `10.1.1.1`, rule 3 would deny it, even though rule 4 generally allows SSH.

### Conclusion

NSGs are a vital part of network security in Azure, helping you control and manage traffic between resources in a VNet, as well as the broader internet. By understanding and using NSGs effectively, you can implement robust security controls, prevent unauthorized access, and monitor traffic to ensure compliance with your security policies.

What Are Service Tags?

Service tags are labels that represent a set of IP address ranges used by a specific Azure service, a group of services, or a specific region.

For example, instead of writing specific IP address ranges for Azure Storage, you can use the Storage service tag, which automatically includes all IP ranges associated with Azure Storage.

Predefined Service Tags:

Azure has several predefined service tags that are associated with common Azure services. These tags are automatically updated by Microsoft to reflect changes in service IP ranges.

Purpose of Service Tags:

Simplify Security Rules: They reduce the complexity of your security rules by abstracting away the need to specify IP ranges.

Maintain Flexibility: Service tags dynamically adjust to IP address changes in the services they represent. You don’t need to manually update your rules if an Azure service changes its IP ranges.

Granular Control: You can use service tags in NSG rules, Azure Firewall policies, route tables, and other network-related resources.

Available Service Tags: Azure offers a variety of service tags for different types of services. Here are a few common ones:

VirtualNetwork: Represents all IP addresses in the Virtual Network, used for communicating between VNets.

AzureLoadBalancer: Represents IP addresses for Azure Load Balancers (used in ingress and egress traffic).

Storage: Represents the IP address range for Azure Storage services (Blob Storage, File Storage, etc.).

SQL: Represents the IP range for Azure SQL Database.

AppService: Represents the IP address range for Azure App Service (Web Apps, etc.).

KeyVault: Represents the IP range for Azure Key Vault.

ServiceBus: Represents IP ranges for Azure Service Bus.

AzureFrontDoor: Represents IP ranges for Azure Front Door service.

ApplicationGateway: Represents IP address range for the Azure Application Gateway.

AzureCloud: Represents the set of IP addresses used for the entire Azure cloud environment.

Storage: Represents IP address ranges for all Azure Storage services.

TrafficManager: Represents the range of IPs for Azure Traffic Manager.

You can see a full list of available service tags by querying Azure documentation or using the Azure Portal.

Azure Application Security Groups (ASGs)
Azure Application Security Groups (ASGs) are a feature in Azure that allows you to group Virtual Machines (VMs) or network interfaces (NICs) based on the application they belong to, rather than their individual IP addresses. This makes it easier to manage and apply network security rules dynamically.

What is an ASG?
An Application Security Group (ASG) is essentially a logical group that you can associate with Azure VMs or NICs. You can then reference these ASGs in Network Security Groups (NSGs) to create more granular and flexible security rules based on application-level grouping, rather than using static IP addresses.

How Does ASG Work?
An ASG is used to represent a set of VMs or NICs that need to be secured together. These VMs or NICs might be part of the same application or tier, and you can apply security rules to all of them by referencing the ASG in NSG rules.

Example of Application Scenarios:
Web Application Tier: A set of VMs running a web application can be grouped into an ASG called WebTier. You can define an NSG rule that allows inbound traffic only from WebTier (the VMs in the web tier) to the backend DatabaseTier.

Database Tier: A set of VMs running the database can be grouped into an ASG called DatabaseTier. You can restrict access to this tier by allowing only traffic from WebTier to reach the database.
